## 二、🔴 高严重度（建议优先修）

### H1 — cache.db 缺 `busy_timeout` / WAL，跨进程会抛 "database is locked"（P0）

**证据**
- `EasyMovie.Data/CacheDbContext.cs:43-46`：`CreateOptions()` **只** `UseSqlite(...)`，**未** `AddInterceptors(BusyTimeoutInterceptor)`。
- 对比 `EasyMovie.Client/DbHelper.cs:68-72`：`MovieDbContext` 的选项**加了** `BusyTimeoutInterceptor.Instance`（该拦截器负责 `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=3000;`，见 `DbHelper.cs:21-49`）。
- **根因是分层错位**：`BusyTimeoutInterceptor` 定义在 `EasyMovie.Client/DbHelper.cs`（**Client 层**，最上层），而 `CacheDbContext` 在 `EasyMovie.Data`（下层）。Data 无法反向引用 Client → cache.db 天然用不上这个拦截器。

**访问面（确有并发）**
- GUI 进程：`EasyMovie.Tools/MovieApi/LocalMovieCache.cs:26,32,46,74,111,...` 每次 `CacheDbContext.Create()`；启动期 `RatingBackfill.Sync`（`DbHelper.cs:318`）。
- 独立进程：`EasyMovie.BackfillRunner/Program.cs:36` 也用 `CacheDbContext.CreateOptions()`。
- 结论：**两个进程**同时读写 `%LocalAppData%/EasyMovie/cache.db`，且双方 `busy_timeout=0`（SQLite 默认）→ 一旦撞锁**立即** `SQLITE_BUSY / "database is locked"`，**不重试、不等待**。`LocalMovieCache.Upsert`（无 try/catch，`LocalMovieCache.cs:94` `ctx.SaveChanges()`）会把异常直接抛给调用方。
- 又因 cache.db 未启用 WAL（默认 rollback journal），**写者会阻塞读者**，进一步放大撞锁概率。
- 触发场景：定时 BackfillRunner（每数小时一次）与 GUI 启动同步/运行时缓存写入重叠时。

**修复**
1. 把 `BusyTimeoutInterceptor` 从 `EasyMovie.Client` **移到 `EasyMovie.Data`**（消除分层错位），Client 改为引用 Data 中的它。
2. `CacheDbContext.CreateOptions()` 增加 `.AddInterceptors(BusyTimeoutInterceptor.Instance)`，与主库一致（WAL + busy_timeout=3000）。
3. 可选：给 `LocalMovieCache` 的写路径加锁冲突重试（`SQLite Error 5` 重试 N 次）。

### H3 — `Movie.FilePath` 无唯一约束，去重靠应用层（TOCTOU 竞态 + 重复导入）✅ 已修复（2026-09-20）

> **修复**：①`MovieConfiguration.cs` 增加 `.HasIndex(m => m.FilePath).IsUnique().HasFilter("FilePath IS NOT NULL")`；
> ②`DbHelper.EnsureIndexes()` 在每次启动（`EnsureInitialized` 顶部 + `EnsureCreated` 后）幂等执行
> `CREATE UNIQUE INDEX IF NOT EXISTS IX_Movies_FilePath ON Movies(FilePath) WHERE FilePath IS NOT NULL;`，
> 并用 try/catch 包裹——**若历史库已存在重复行，索引创建失败也不会自动删数据**（交由用户人工处置，绝不静默删库）；
> ③`ImportExportService` 的 JSON 导入与全量还原增加 `knownPaths` 去重（按 FilePath 跳过重复）。

**证据**
- `EasyMovie.Data/Configurations/MovieConfiguration.cs:68-73`：只有 Title/Year/Rating/WatchStatus/CategoryId **普通索引**，无 `HasIndex(FilePath).IsUnique()`。
- 去重是"先查后插"：`App.xaml.cs:434-443`（`Where(FilePath==x).FirstOrDefault()` 再 `Add`）；`FolderImportService`/JSON 导入同理，且 `ImportMoviesFromJsonAsync` **完全没有去重**。
**影响**
- `FolderWatcher` 的 `Created`/`Changed`/`Renamed` 多事件 + 轮询兜底可能在毫秒级并发命中同一文件 → 两个线程都"查不到"→ **插入两条重复影片**。
- 重复导入 JSON/CSV 备份 → 整库翻倍，且无外键/唯一约束拦截。
**修复**：加**过滤唯一索引** `CREATE UNIQUE INDEX UX_Movies_FilePath ON Movies(FilePath) WHERE FilePath IS NOT NULL;`（迁移到 `EnsureMovieColumns`/首次初始化），保存时捕获 `DbUpdateException` 作为最后防线；JSON/CSV 导入按 FilePath（或 Title+Year）去重。

## 三、🟠 中严重度

### M1 — 可空引用告警被整体抑制，nullable 形同虚设 ✅ 已修复（2026-09-20）

**原问题**
`EasyMovie.Client.csproj:13` 与 `EasyMovie.Tools.csproj:19` 的 `<NoWarn>` 抑制了 `CS8625;CS8602;CS8604;CS8629;CS8601`（可空注解缺口）与 `CS4014`（未 await 的 Task）。**开了 `Nullable=enable` 却把它的产出全部关掉**，等于放弃了编译器对 NRE 的静态防护；`CS4014` 被抑制则让 fire-and-forget 彻底隐形。

**实测告警面（去掉抑制后全量重编得到的真实数字，远小于预期）**

| 项目 | 唯一告警 | 构成 |
|------|---------|------|
| Tools | **14** | 10×CS8602 + 3×CS8604 + 1×CS8601 |
| Client | **8** | 4×CS4014 + 2×CS8625 + 1×CS8602 + 1×CS8604 |

**⚠️ 关键发现：Tools 的 10 条 CS8602 是同一处根因的级联，不是 10 个缺陷**
`DoubanBackfillService.cs:131` 写了 `if (rep != null && rep.StoppedByThrottle) break;`，而 `rep` 是方法内 `new DoubanBackfillReport{...}` 出来的**局部量、恒非 null**。这句多余判空把该变量的可空流状态污染成 `MaybeNull`，于是其后每一处 `rep.`（`rep.Skipped++`、`rep.Filled++`、`rep.StoppedByThrottle=…`）都被判为"解引用可能出现空引用"。**删掉 `rep != null &&` 一处，10 条告警全部消失。**
> 教训：告警条数 ≠ 缺陷个数。先按 file 归类、再找共同根因，往往一处修复清掉一片；逐条盲改会写出 10 份防御性判空，污染代码且掩盖真问题。

**逐项修复（全部按真实根因，非 `!` 或 `?? ""` 式敷衍）**

| 位置 | 告警 | 真因 | 修复 |
|------|------|------|------|
| `DoubanBackfillService.cs:131` | 10×CS8602 | 对恒非 null 的局部量做判空，污染流分析 | 删除多余的 `rep != null &&` |
| `DoubanApiClient.cs:403` | CS8604 | `IsTemplateOrLabel(string value)` **契约本身是「null→true」**（首行 `IsNullOrWhiteSpace` 即返回 true，注释亦言明），签名却声明为非空 | 形参改 `string?`，让签名与契约一致（同时消除 `OriginalTitle` 可能为 null 的调用点告警） |
| `AlternativeRatingBackfill.cs:68-73` | 2×CS8604 | 对**静态属性** `AppSettings.TmdbApiKey` 做 `IsNullOrWhiteSpace` 判断，属性可被重新求值 → 编译器不据此窄化后续访问 | 先捕获到局部量 `tmdbKey`/`omdbKey`，判空与传参都用局部量 |
| `MovieApiService.cs:61` | CS8601 | `Movie.Title` 非空，但 `StripHtml(...)` 返回 `string?` | `StripHtml(result.Title) ?? string.Empty` 显式满足非空契约 |
| `DashboardView.xaml.cs:519` | CS8602 | `_context` 是**字段**，可空流分析在 `await`/方法调用后会重置字段状态 | 捕获到局部量 `ctx` 后判空一次，贯穿两个查询 |
| `MovieListView.xaml.cs:1988` | CS8604 | `if (selected[0].FilePath != null) Mark(selected[0].FilePath)` —— 索引器**再求值**，上一行的判空结论无法复用 | `var singlePath = selected[0].FilePath;` 后再判空 |
| `MovieListView.xaml.cs:1998` | 2×CS8625 | 内部调用 `BatchDelete_Click(null, null)` 给 WPF 事件形参强塞 null 以复用逻辑 | 抽出无参核心方法 `DeleteSelectedMoviesAsync()`；`BatchDelete_Click` 变薄壳，内部调用改 `await DeleteSelectedMoviesAsync()` |
| 4 处 `Dispatcher.BeginInvoke` | 4×CS4014 | `BeginInvoke` 返回可 await 的 `DispatcherOperation`，但语义是**有意 fire-and-forget 的 UI 投递** | 显式 `_ = ...` 丢弃，表达意图并恢复 CS4014 检查（未来真正漏 await 会被抓到） |

**结果**：`EasyMovie.Tools.csproj` 的 `<NoWarn>` **整行删除**；`EasyMovie.Client.csproj` 收敛为 `<NoWarn>NU1701;CA1416</NoWarn>`（仅剩两项无法修复的真误报：传递依赖包元数据不完整、MDIX 被平台兼容性分析器误判）。全解决方案 **0 错 0 警**，测试 **552/552**。

- `EasyMovie.Client/Helpers/PosterCache.cs` **没有 `Delete`**，全仓也无任何调用点删除 `Posters/{id}.jpg`（grep 仅见 `Save`/`Load*`）。删除影片（`MovieService.DeleteAsync`）/ 重复合并后，`{id}.jpg` 永久驻留 → 磁盘缓慢泄漏。
- `EasyMovie.Client/Views/MovieDetailView.xaml.cs:122-123`：新增影片时 `PosterCache.Save(m.Id, ...)`，此刻 `m.Id == 0`（`AddAsync` 在 `:133` 才赋真实 Id）→ 海报被写进 `0.jpg`，后续按真实 Id 读盘必 miss（靠下次启动 `MigrateFromDb` 自愈，但本次会话一直 miss + 产生孤儿 `0.jpg`）。
**修复**：`PosterCache.Delete(id)`；在删除影片/合并去重路径调用；`MovieDetailView` 把 Save 移到 `AddAsync` 之后用真实 Id。

### M4 — 全量还原的长事务持有 SQLite 写锁，并发写会超时/触发 UI 卡顿
`ImportExportService.ImportFullDataFromJsonAsync` 用 `BeginTransactionAsync` 包住整段还原（`:254`），期间分类/标签逐条 `SaveChanges`（`:270,284`），整体提交前 SQLite **写锁一直持有**。此时 `FolderWatcher` 的自动入库（另一个 `MovieDbContext`）会排队等 `_writeLock`→再等 SQLite（busy_timeout 3s）→ 超时即抛。大备份还原更明显。
**修复**：还原走"批量 `AddRange` + 单次 `SaveChanges`"缩短持有时间；或先写库外临时表/文件再原子切换；至少给 UI 一个还原中的模态提示，并让 FolderWatcher 在还原期间暂停。

### M5 — 关键词搜索用前导通配 `%kw%`，索引全部失效
`MovieRepository.SearchAsync:115-121`：`m.Title.ToLower().Contains(kw)` 等 → 生成 `LIKE '%kw%'`（前置 `%`）无法走 `Title` 索引，且 `SearchIndex` 列虽存在也只用于同样的 `Contains`（`:120`）。当前 290 行全表扫无感，但设计上不可扩展。
**修复**：若要保留模糊搜索，至少对 `SearchIndex` 做前缀检索（`LIKE 'kw%'` 可走索引），或引入 FTS5 虚表；`.ToLower()` 交客户端/改用 `COLLATE NOCASE`。

### M6 — 同步 `SaveChanges()` 在 UI 线程上有死锁面 🔵 已取证：死锁不可达，已加固 + 固化不变量（2026-09-20）

**原判断**：`MovieDbContext.SaveChanges` 用阻塞 `_writeLock.Wait()`（`_writeLock` 是 **`static`**，全进程共享）。若 UI 线程走同步 `SaveChanges`，而锁被后台线程持有且后者正 `Dispatcher.Invoke` 回 UI → sync-over-async 死锁。

**取证过程与结论（不靠推测）**
1. **列出全部生产代码的同步 `SaveChanges()` 调用点**：`VideoPlayerHost.xaml.cs:942`（**UI 线程**，退出播放/播完保存进度）、`DbHelper.cs:474,538`（启动播种）、`RatingBackfill.cs:79`、`TextCleanupMigration.cs:92`（启动迁移）、`LocalMovieCache`（Tools）、`AlternativeRatingBackfill.cs:216`（独立进程）。其中只有 `VideoPlayerHost` 是热路径 UI 线程。
2. **死锁的必要条件**是"持锁线程阻塞式等待 UI 线程"。逐一核对全部阻塞式 `Dispatcher.Invoke` 调用点（8 处），**没有一处在持锁期间执行**：
   - `App.xaml.cs:374`（系统主题变更，不碰 DB）；
   - `MovieListView:1274`（手动搜索弹窗，位于网络抓取阶段、写库之前）、`2359/2370`（读服务返回后的 UI 线程续体，`Dispatcher.Invoke` 从 UI 线程调用是内联执行）；
   - `SettingsView:778/783`（只读队列统计）、`DuplicateResultDialog:32`（构造，UI 线程）；
   - `VideoPlayerHost:1275/1331`（抽帧后台任务的收尾，该任务**不写 DB**——全文件只有 942 一处 `SaveChanges`）。
   - 后台写库主路径（FolderWatcher 导入）收尾用的是**非阻塞** `BeginInvoke`。
3. **结论**：**硬死锁当前不可达**。真实症状只是"退出播放时 UI 线程可能短暂阻塞在进程级写锁上"（持锁方为单次 `SaveChanges`，WAL + `busy_timeout=3000` 在位，通常毫秒级）。

**已做的两处低风险加固（不做侵入式重构）**
- `VideoPlayerHost.SavePositionToDb`：原用 `ctx.Movies.Find(id)` → **整行含 PosterData BLOB（~86KB/部）物化**再写回。改为项目既定的**桩实体单列更新**（`Attach(new Movie{Id})` + `Entry.Property(PlaybackPosition).IsModified = true`），把一次读放大+写压缩成单列 `UPDATE`，**直接缩短 UI 线程阻塞在写锁上的时间**，也契合"不物化海报 BLOB"的性能契约。
- `MovieDbContext._writeLock`：补上**不变量警示注释**——"持锁期间绝不允许阻塞式等待 UI 线程；后台写库+界面更新请用 `BeginInvoke`/`InvokeAsync`"。这比改行为更能防未来回归：下一个在里面写 `Dispatcher.Invoke` 的人会先看到警告。

**未采纳的建议**：REVIEW 原先提议"Dispose 掉同步重载强制全异步（`throw NotSupportedException`）"。**不采纳**——启动迁移/播种等路径依赖同步语义，强改会波及启动流程，而收益（消灭一个当前不可达的死锁）不成比例，违背项目的安全增量原则。

### M7 — 静态 Service Locator + 混杂的手工 `new`，生命周期不可控 ✅ 部分修复（2026-09-20）

> **已修**：`App.OnExit` 增加 `(Services as IDisposable)?.Dispose()`（try/catch 包裹），单例释放逻辑得以执行。
> **未修**（仍待办）：`OnNewFileDetected` 手工 `new FolderImportService()/DoubanApiClient()` 绕过 DI；
> `MovieDbContext`/仓储注册为 Transient 被长生命周期 ViewModel 持有 → 隐式内存增长。
- `App.xaml.cs:34` `Services` 为静态 `IServiceProvider`，`OnExit` **从不 Dispose**（`:244-263`）→ 单例的释放逻辑不会跑。
- `App.xaml.cs:445-460`：`OnNewFileDetected` 直接 `new FolderImportService()` 与 `new DoubanApiClient()`，绕过 DI；`DoubanApiClient` 内部 `new HttpClient`（见 L4）。
- `MovieDbContext`/各 Repository 注册为 **Transient**（`:270-275`）；长生命周期 ViewModel 持有后，其 `DbContext` 会长期跟踪实体（`GetByIdAsync` 是跟踪查询），造成隐式内存增长。
**修复**：`Services` 在 `OnExit` `(Services as IDisposable)?.Dispose()`；API 客户端经 DI 提供单例/工厂；长生命周期视图用 `IDbContextFactory<MovieDbContext>` 或 `AsNoTracking` + 短生命周期仓储。
