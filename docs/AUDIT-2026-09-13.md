### P1-4 · `SearchAsync` 的集合 JOIN 是潜伏的性能地雷

**位置**：`EasyMovie.Data/Repositories/MovieRepository.cs:104-109`

```csharp
var query = _context.Movies
    .AsNoTracking()
    .Include(m => m.Category)
    .Include(m => m.MovieTags)      // ← 集合导航，产生 JOIN
        .ThenInclude(mt => mt.Tag)
```

**实测（真实库）**：

| 项 | 数值 |
|---|---|
| Movies | 290 部 |
| 有海报的电影 | 288 部，海报合计 **24.29 MB**（占库 99.4%） |
| 平均单张海报 | **86.4 KB** |
| MovieTags 链接数 | **0** ← 当前尚未放大 |
| JOIN 放大倍数（当前） | **1.00x** |

**为什么现在没事、将来会炸**：当前 `MovieTags` 是空表，JOIN 不放大行数。
一旦用户开始打标签（比如每部 3 个标签），单页 20 部 → JOIN 出 60 行，
**每行都携带 86.4 KB 的 PosterData → 单页要从 SQLite 读约 5 MB**（现在是 1.7 MB）。

这与项目既定的**数据访问性能契约**（"集合 JOIN 让 BLOB 按标签数重复读"）冲突。

**行动**：列表页改成两阶段 —— 先窄投影取这一页的 Movie 元数据（不含 PosterData），
海报走已有的 `PosterCache` 按需加载；标签另行批量查 `MovieTags` 小表。
建议加一条守卫测试：模拟每部 3 标签，断言单页读取字节数不随标签数线性增长。
