## 二、发现表（按严重度分类，含未修项）

### 🔴 严重 / 高
- **（已修）F1 全量备份还原丢标签**：见上。这是本次唯一"严重"级真缺陷，已修。

### 🟠 一般 / 中
- **F2 CSV 导入无 FilePath（数据完整性）** — `ImportExportService.cs` `CsvMovieRecord` / `MapFromCsvRecord` (~388)。CSV 模型无 `FilePath` 列，导入影片 `FilePath=null` → 不可播放，且去重（按 FilePath）失效、重复导入 CSV 会建重复行。
  - 复现：导出 CSV→清空库→重新导入 CSV → 影片无媒体路径、无法播放、可重复导入。
  - 建议：CSV 导入定位为"目录编辑"，UI 显式提示"CSV 导入影片不含媒体文件"；或在 `CsvMovieRecord` 增加 `FilePath` 列并在导入时按路径去重。**设计取舍，本次未改**（无可靠 FilePath 来源）。
- **（已修）F3 导入 SaveChanges 未兜底**：见上。
- **（已修）F6 解码切换 LibVLC 泄漏**：见上。
- **G 启动期 Schema 竞态（EF+SQLite 加列 footgun，潜在严重）** — `DbHelper.cs` `WarmupAsync`/`EnsureInitialized` (~93/~109)。契约：任何物化 `Movie` 的查询必须在 `WarmupAsync` 完成 ALTER 之后；否则真实库缺列 → `SQLite Error: no such column`。当前依赖"各视图查询前 `await DbHelper.WarmupAsync()`"的人为契约，脆弱。
  - 复现（风险）：若某视图在后台预热线程 ALTER 完成前查询 `Movies`（含新列），触发 `no such column` 崩溃。
  - 建议：在 `MovieDbContext` 首次查询前强制同步 `EnsureInitialized()`（或给 `Movie` 实体加列加全局护栏），消除"每个视图都必须记得 await"的脆弱约定。属设计风险，标注待后续收口。
- **H 仓库 Include(MovieTags) 潜伏性能雷（一般，当前 inert）** — `MovieRepository.cs:21,30,45,107` `GetAllAsync`/`SearchAsync` 仍 `Include(m => m.MovieTags)`。当前 `MovieTags=0` 无影响；一旦用户打标签，海报 `PosterData`（占库 99.4%）会按标签数重复物化（3 标签 → 单页 20 部约 5MB）。
  - 建议：移除列表/搜索查询不需要的 `Include(MovieTags)`，改窄投影或按需单独取标签。功能上线即爆，建议优先于"标签"功能开放前修。

### 🟡 低
- **D 全量还原异常笼统** — `ImportFullDataFromJsonAsync` 整个导入包在单个 `try/catch` 返回"还原失败"，不指明哪条记录。事务回滚干净，可接受；建议失败信息带上 `backup.Movies` 索引以便排查。
- **F 应用退出未 Dispose static LibVLC** — `_libVLC` 为 static，进程退出时未显式 `Dispose`；OS 回收，低优。
- **J 缩略图抽帧降级** — `GenerateThumbnails` 在 `Application.Current==null` 时跳过离屏窗口（仅日志降级），非 GUI 测试环境预期行为。
- **编码已验证无误** — CSV 导出用 `Encoding.UTF8`（含 BOM），`ImportMoviesFromCsvAsync` 读 `Encoding.UTF8`（自动识别 BOM）；Excel(GBK 区) 可正常读取中文，**无乱码**（原先怀疑点排除）。

## 五、按建议修复记录（2026-09-20 执行）

用户确认"按你建议修复"。已落地两个 P1 + P3-D，构建 0 错 0 警、测试 552/552 绿。

### 已修：H — MovieRepository 的 Include(MovieTags) 性能雷
- 文件：`EasyMovie.Data/Repositories/MovieRepository.cs`
- 修复：`GetAllAsync` / `GetByIdsAsync` / `SearchAsync` 三处批量查询的 `Include(MovieTags)` 后追加 **`.AsSplitQuery()`**。
- 原理：原 `Include` 触发 `Movie × 标签数` 笛卡尔 JOIN，把 `PosterData`（占库 99.4%）按标签数重复物化；用户一打标签，单页 20 部会重复读数百 KB~数 MB。`AsSplitQuery` 把 Include 拆成独立查询，每部电影海报只加载一次，标签/分类照常填充，**行为零变化**。

### 已修：G — 启动期 Schema 竞态（EF+SQLite 加列 footgun，根因修复）
- 文件：`EasyMovie.Client/DbHelper.cs`
- 根因：Movie 列 ALTER 原先只写在 `EnsureInitialized` 的"首次初始化"分支（受 `InitFlagPath` 守护）。返回用户（InitFlag 已存在、首活被跳过）代码升级新增列后**永远拿不到该列** → 任何物化 Movie 查询命中 `no such column` 崩溃。
- 修复：
  1. 抽出 **`EnsureMovieColumns()`**：每次启动、与 InitFlag 脱钩，先 `PRAGMA table_info` 探表再条件 ALTER 全部已知 Movie 列（幂等）。
  2. `EnsureInitialized` 顶部调用它（覆盖返回用户）；并在 `EnsureCreated()` 之后补跑一次（覆盖从旧版迁移来的老库——`EnsureCreated` 对已存在库不改 schema）。
  3. `EnsureRatingSchemaAndBackfill` 改为委托 `EnsureMovieColumns()` 做列存在性，去掉重复的 ExternalRating/RatingSource ALTER。
- 效果：新增列在下次启动即被补齐，**无需删初始化标记、无需人工干预**，从根上消除该竞态。原"各视图查询前 await WarmupAsync"契约仍保留为双重保险。

### 已修：P3-D — 全量还原错误信息细化
- 文件：`ImportExportService.cs` `ImportFullDataFromJsonAsync`
- 修复：还原中断时错误信息带上中断位置影片标题（`还原失败（中断于影片「X」）`），保留"整体回滚"语义不变，仅提升可定位性。

- **P3-F static LibVLC 退出释放**：进程退出由 OS 回收原生资源，且播放中 Dispose 有崩溃风险，维持现状。
